# نشر الويب — ولماذا ظهرت صفحة بيضاء

## الخلاصة

الصفحة البيضاء ليست عطلًا في واجهة تسجيل الدخول، بل **التطبيق لم يبدأ أصلًا**.
الشاشة تُرسم من JavaScript، فإذا لم يُحمّل `main.dart.js` أو لم يجد Firebase
أو حُجب ملف المحرك (CanvasKit) — لا يبقى في الصفحة شيء، فتظهر بيضاء بلا رسالة.

لهذا أضفنا **حارس إقلاع**: صفحة `index.html` تعرض شاشة تحميل بعدّاد ثوانٍ،
وإذا لم ترسم الواجهة خلال **90 ثانية** تعرض لوحة بالعربية فيها التشخيص وثلاثة
خيارات — بدلًا من الصفحة البيضاء.

| الحالة | ما يظهر |
|---|---|
| التحميل جارٍ | `Loading the app… 12s` |
| بدأ المحرك | `Opening the sign-in page… 18s` |
| قبل الرسم | شاشة بشكل صفحة الدخول: `Azal Soft Platform` · `Username or email` · `Password` · `Sign in` |
| خطأ في `main.dart.js` أو `canvaskit` | اللوحة بعد 8 ثوانٍ |
| 90 ثانية بلا رسم | اللوحة + زر **متابعة الانتظار** |
| ظهرت الواجهة لاحقًا | تُزال اللوحة تلقائيًا |

> **الشبكة البطيئة ليست عطلًا.** إن ظهرت اللوحة فاضغط «متابعة الانتظار» أولًا؛
> «مسح التخزين» آخر ما يُجرَّب لأنه يعني تنزيل التطبيق كاملًا من جديد.

## أولًا: أعد البناء والنشر بالأمر الصحيح

أغلب حالات الصفحة البيضاء سببها نشر نسخة ناقصة أو نسخة قديمة.

```bash
# 1) بناء موثوق (يفحص المخرجات بنفسه)
bash tool/build_web.sh

# 2) النشر
firebase deploy --only hosting
```

أو يدويًا:

```bash
flutter build web \
  --release \
  --base-href "/" \
  --no-web-resources-cdn
```

### لماذا هذان الخياران؟

| الخيار | السبب |
|---|---|
| `--base-href "/"` | الموقع على جذر النطاق. بدونه تُطلب الملفات من مسار خاطئ فتفشل كلها. |
| `--no-web-resources-cdn` | ينسخ CanvasKit داخل `build/web/canvaskit/` بدل تحميله من `gstatic.com` وقت التشغيل. **حجب `gstatic.com` = صفحة بيضاء بلا أي رسالة.** |

> إن كان الموقع على مسار فرعي (مثل GitHub Pages: `/my_water/`) فاستخدم
> `--base-href "/my_water/"` بدل `/`، أو مع السكربت:
> `BASE_HREF=/my_water/ bash tool/build_web.sh`.

### ويندوز — Git Bash (خطأ `C:/Program Files/Git/`)

إن ظهر:

```
Received a --base-href value of "C:/Program Files/Git/"
--base-href should start and end with /
```

فالسبب أن Git Bash (MSYS) يحوّل كل وسيط يبدأ بـ `/` إلى مسار ويندوز قبل أن
يصل إلى Flutter. ليس عيبًا في مشروعك ولا في نسخة Flutter.

`tool/build_web.sh` صار يعطّل هذا التحويل بنفسه:

```bash
export MSYS_NO_PATHCONV=1
export MSYS2_ARG_CONV_EXCL="*"
```

وإن شغّلت Flutter يدويًا فافعل الشيء نفسه:

```bash
MSYS_NO_PATHCONV=1 flutter build web --release --base-href "/" --no-web-resources-cdn
```

كذلك لم تعد الرسالة «لم يُقبل O4» تظهر إلا إذا كان الفشل متعلقًا فعلًا
بخيار `--dart2js-optimization`؛ أي خطأ آخر يتوقف عنده السكربت برسالته الحقيقية.

> رسالة `48 packages have newer versions incompatible with dependency constraints`
> من `flutter pub get` معلومة فقط ولا تمنع البناء. لا تُحدِّث
> `firebase_core`/`cloud_firestore`/`firebase_auth` إلى الإصدارات الكبرى
> الجديدة قبل إعادة اختبار التطبيق كله: واجهاتها تتغيّر.

## ثالثًا: امسح نسخة المتصفح القديمة

Flutter web يستخدم Service Worker. بعد كل نشر قد يبقى المتصفح على النسخة القديمة
فيظهر خطأ أو صفحة بيضاء رغم أن النشر سليم.

شاشة الخطأ الجديدة فيها زر **«مسح التخزين وإعادة التحميل»** يمسح الـ caches
ويسجّل الـ service worker من جديد. أو يدويًا:

- Chrome/Edge: `F12` ← تبويب **Application** ← **Storage** ← *Clear site data*.
- أو نافذة تصفّح خاصة: إن عملت هنا فالسبب ذاكرة المتصفح حصرًا.

كما أضفنا في `firebase.json` رؤوس `Cache-Control: no-cache` لـ
`index.html` و`flutter_bootstrap.js` و`flutter_service_worker.js`
و`version.json` و`main.dart.js` — فلم يعد المتصفح يحتفظ بنسخة قديمة من نقطة الدخول.

## خامسًا: ماذا تفعل إن بقيت الصفحة بيضاء

1. **افتح `F12` ← Console** وصوّر أول سطر أحمر. سيحدد السبب فورًا.
2. إن ظهرت شاشة الخطأ الجديدة، انسخ النص الموجود في الصندوق الأسود
   (`URL` · `baseURI` · حالة كل ملف) وأرسله.

ويُقرأ التشخيص هكذا:

| السطر في التشخيص | السبب |
|---|---|
| `engine: started` و`canvas: no` | المحرك يعمل والرسم لم يبدأ — انتظر أو أعد التحميل |
| `canvas: no` + `main.dart.js: 404` | البناء غير منشور |
| `canvas: no` + `main.dart.js: 200` | فشل تحميل CanvasKit من `gstatic.com` → أعد البناء بـ `--no-web-resources-cdn` |
| `PROBLEMS: تعذّر تحميل الملف: …canvaskit.wasm` | نفس السبب أعلاه |
| `PROBLEMS: JS: …` | استثناء Dart/JS أثناء الإقلاع — نصه يحدد الملف |
| `canvas: yes` ومع ذلك بيضاء | الواجهة رُسمت لكن الشاشة الأولى فارغة — مشكلة في الكود لا في النشر |

## سرعة فتح صفحة الدخول

أول فتح ينزّل التطبيق فعلًا، فلا بد أن يأخذ وقته. المتكرر يجب أن يكون شبه فوري.
كان هناك سببان يمنعان ذلك:

| السبب | الأثر | الإصلاح |
|---|---|---|
| `Cache-Control: no-store` على `main.dart.js` | المتصفح **ممنوع** من الاحتفاظ بالملف، فينزّل التطبيق كاملًا في كل زيارة | صار `no-cache` وحدها: يُعيد المراجعة فيأتي `304` بمئات البايتات |
| Tesseract.js في رأس الصفحة | ~1 ميغابايت تُنزَّل مع كل فتح ولا تُستخدم إلا في قراءة العدادات | صار يُطلب عند أول عملية قراءة عبر `ensureTesseract()` |

كما صارت ملفات المحرك والخطوط والأصول تُخزَّن سنة كاملة:

| المسار | الرأس |
|---|---|
| `/index.html` · `/flutter_bootstrap.js` · `/version.json` · `/main.dart.js` | `no-cache` |
| `/canvaskit/**` · `/assets/**` · `**/*.wasm` · الصور والخطوط | `public, max-age=31536000, immutable` |

وقُدّمت اتصالات DNS/TLS مسبقًا إلى `gstatic` و`identitytoolkit` و`firestore`
حتى لا تُدفع تكلفتها عند أول تسجيل دخول.

### كيف تقيس الفرق

`F12` ← **Network** ← `Ctrl+R`:

| المقياس | قبل | بعد |
|---|---|---|
| حجم `main.dart.js` | يُنزَّل كاملًا كل مرة | `304` بعد الزيارة الأولى |
| `tesseract.min.js` عند فتح الصفحة | ~1 MB | لا يُطلب أصلًا |
| `canvaskit.wasm` | يُعاد طلبه | من الذاكرة لسنة |

## فتح أسرع لصفحة الدخول (هذه الحزمة)

كان الفتح يتأخر لأن **كل** شيء كان ينتظر كل شيء:

| ما كان يحدث | الأثر |
|---|---|
| `main()` ينتظر `Firebase.initializeApp` قبل `runApp` | لا يُرسم شيء حتى تنتهي التهيئة |
| كل الشاشات والتقارير داخل `main.dart.js` واحد | المتصفح ينزّل التطبيق **كله** قبل أن يظهر نموذج الدخول |
| `SplashScreen` يدور ثم ينتقل إلى الدخول | ثوانٍ إضافية بعد انتهاء التنزيل أصلًا |
| شاشة انتظار عامة بلا ملامح | الإحساس بأن «الصفحة لا تفتح» |

ما صار الآن:

| التغيير | الملف | الفائدة |
|---|---|---|
| `runApp` فورًا، والتهيئة في الخلفية | `lib/main.dart` · `lib/services/app_bootstrap.dart` | أول إطار يُرسم بلا انتظار |
| الويب يفتح على `LoginScreen` مباشرة (بلا Splash) | `lib/main.dart` | لا شاشة انتقال أصلًا |
| زر الدخول يُفعَّل لحظة جهوزية Firebase مع شريط صغير | `lib/screens/login_screen.dart` | المستخدم يكتب بياناته أثناء التهيئة |
| شاشات ما بعد الدخول **تحميل مؤجَّل** (`deferred`) | `login_screen.dart` · `splash_screen.dart` | ملف الإقلاع يصغر كثيرًا |
| شاشة أولى بشكل صفحة الدخول تُرسم من HTML | `web/index.html` | تظهر خلال أقل من ثانية وتذوب عند رسم الواجهة |
| `--dart2js-optimization O4` | `tool/build_web.sh` | ملف JS أصغر |
| رؤوس `no-cache` لأجزاء `main.dart.js_*` | `firebase.json` | تحديث الشاشات المؤجَّلة يصل للمستخدم |

### ما الذي ينزّله المستخدم الآن قبل أن يرى الدخول؟

1. `index.html` (شاشة الانتظار تظهر فورًا).
2. `flutter_bootstrap.js` + محرك Flutter (`canvaskit`).
3. `main.dart.js` — صار يحتوي شاشة الدخول وFirebase فقط.

أما التقارير والشاشات و OCR وقراءة العدادات فتُنزَّل **بعد** نجاح الدخول،
ويظهر على الزر نص المرحلة («Loading the dashboard…») أثناء تنزيلها.

### أرقام تقيسها بنفسك

```bash
bash tool/build_web.sh      # يطبع حجم main.dart.js وحجم الأجزاء المؤجَّلة
```

ثم في المتصفح: `F12` ← **Network** ← أعد التحميل، ورتِّب بالحجم.

| المقياس | المتوقع بعد هذه الحزمة |
|---|---|
| ظهور أول شاشة | أقل من ثانية (من HTML) |
| `main.dart.js` | أصغر بمقدار ما يوفر حذف الشاشات من الحزمة الأولى |
| `main.dart.js_*.part.js` | لا يُطلب منها شيء قبل تسجيل الدخول |
| الزيارة الثانية | شبه فورية (Service Worker + `max-age` لسنة للمحرك والخطوط) |

> إن طال الانتظار رغم ذلك فالشبكة هي الحد: أول فتح لا بد أن ينزّل المحرك.
> راقب حجم `main.dart.js` في تبويب Network؛ إن تجاوز 3 ميغابايت فهناك
> مكتبة ثقيلة استُوردت استيرادًا مباشرًا من مسار الدخول — اجعلها `deferred`.

### تحقّق واحد إضافي: هل ملف المحرك يُضغَط؟

بعد النشر، افتح في المتصفح:

```
https://water-567bb.web.app/canvaskit/canvaskit.wasm
```

في `F12` ← **Network** ← اضغط على الملف ← **Response Headers**، ويجب أن ترى:

```
content-encoding: br   (أو gzip)
```

وجودها يعني أن الملف يُنزَّل مضغوطًا (~700 كيلوبايت بدل ~1.5 ميغابايت).
وغيابها يعني أن CanvasKit يُنزَّل خامًا، وهو أحد أكبر أسباب البطء:

```bash
# للتأكد من الطرفية
curl -I -H "Accept-Encoding: br,gzip" \
  https://water-567bb.web.app/canvaskit/canvaskit.wasm | grep -i content-encoding
```

إن لم تظهر، فالحل الأسرع إبقاء CanvasKit على شبكة Google (احذف
`--no-web-resources-cdn`) بشرط ألّا تكون `gstatic.com` محجوبة عند المستخدم.

## قراءة العدادات لا تُخرِج أرقامًا (OCR)

### ما صار في هذه الحزمة

| المشكلة السابقة | الإصلاح |
|---|---|
| فشل صامت: سبع علامات استفهام بلا سبب | شريط حالة يشرح السبب + قسم **«تفاصيل القراءة (للدعم)»** يعرض المحرك والمصدر وآخر خطأ |
| محرك Tesseract يُطلب من مصدر واحد فقط | ثلاث محاولات: `web/ocr` المحلي ← jsDelivr ← unpkg، مع مسار بديل لملف اللغة |
| لا مهلة: قد تُعلَّق الشاشة على شبكة بطيئة | مهلة لكل محاولة (20 ثانية للسكربت، 45 للمحرك) برسالة واضحة |
| رفض كل القراءات المنخفضة ⇒ لا شيء إطلاقًا | أفضل نص من 6/7 أرقام يُعرض **مقترحًا للمراجعة** بدل لا شيء (لا يُعتمد تلقائيًا) |

### إن ظهرت «تعذّرت القراءة التلقائية»

افتح قسم **«تفاصيل القراءة (للدعم)»** واقرأ السطر الأول:

| السطر | المعنى | الحل |
|---|---|---|
| `engine: failed` | تعذّر تنزيل المحرك من كل المصادر | شغّل `bash tool/fetch_ocr_assets.sh` ثم أعد النشر |
| `engine: loaded` + `worker: not created` | المحرك موجود لكن ملف اللغة/النواة لم يُنزَّل | نفس الحل أعلاه (يفي بالغرض دون إنترنت) |
| `engine: loaded` + `worker: ready` + `error` فارغ | المحرك يعمل والصورة غير واضحة | أعد القص على نافذة الأرقام فقط بإضاءة أفضل |
| `method: cells` مع `digit confidence` منخفضة | قراءة غير واثقة | صحّح الخانة الخاطئة يدويًا؛ الشاشة تُلزم بالمراجعة |

### تشغيل المحرك بلا إنترنت (موصى به لليمن)

```bash
bash tool/fetch_ocr_assets.sh    # ينزّل ~11 ميجابايت إلى web/ocr
bash tool/build_web.sh
firebase deploy --only hosting
```

بعد ذلك تعمل قراءة العدادات من موقعك نفسه بلا اعتماد على jsDelivr أو
`tessdata.projectnaptha.com`. الملفات لا تُطلب إلا عند أول قراءة عداد،
وليست جزءًا من فتح شاشة الدخول. التفاصيل في `web/ocr/README.md`.

## تقليص حزمة ما قبل الدخول: إخراج Firestore منها

بعد التقسيم الأول بقي `main.dart.js` عند **3.1 ميجابايت**، والسبب أن
`cloud_firestore` كان لا يزال داخل الحزمة الأولى: شاشتا الدخول والإقلاع
تستوردانهما مباشرة، والأولى تحتاجهما فقط **بعد** نجاح كلمة السر.

| قبل | بعد |
|---|---|
| `login_screen` يستورد `cloud_firestore` و`gm_dashboard_service` | لا يستورد سوى `firebase_auth` + `gm_roles` + `sign_in_result` |
| قراءة وثيقة المستخدم داخل الشاشة | في `services/sign_in_flow.dart` — **تحميل مؤجَّل** |
| `GmRoles` داخل ملف يستورد Firestore | `services/gm_roles.dart` بلا أي استيراد |

### توزيع الملفات الآن

| الملف | الحزمة | يحتوي |
|---|---|---|
| `main.dart.js` | الأولى | Flutter + Firebase Auth + شاشة الدخول |
| `main.dart.js_1…3.part.js` | مؤجَّلة | الشاشات + **Firestore** + قراءة الوثيقة |

النتيجة: `cloud_firestore` لا يُنزَّل قبل الدخول إطلاقًا، ويُطلب في
لحظة الضغط على الزر (يظهر على الزر: `Checking your account…` ثم
`Loading the dashboard…`)، مع تحميل صامت يبدأ بعد 5 ثوانٍ من ظهور
شاشة الدخول.

### كيف تتحقق

```bash
ls -lh build/web/main.dart.js
du -ch build/web/main.dart.js_*.part.js | tail -1
```

المتوقع: `main.dart.js` **أصغر من 3.1M**، ومجموع الأجزاء **أكبر من
1.2M** — فما خرج من الأولى دخل في الثانية، ولا شيء يضيع:

| المقياس | قبل | بعد (متوقع) |
|---|---|---|
| `main.dart.js` | 3.1M | ~2.7–2.9M |
| أجزاء ما بعد الدخول | 1.2M | ~1.5–1.7M |
